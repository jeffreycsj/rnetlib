# 游戏运行时恢复与 Poll 健壮性规格

## 需求概述

修复 wire-v4 恢复在版本协商完成前提前作废旧会话的问题，并保证游戏事件积压或零容量轮询时，认证控制、心跳、时钟和版本协商仍能推进。允许明文业务时，无法认证的非法 envelope 只累计低基数计数并丢弃，不向游戏循环放大攻击流量。

## 行为规格

### 正常流程

- 当 wire-v3 恢复的传输会话已打开时，系统应保持现有行为：立即以新句柄接管并发布 `SessionResumed`。
- 当 wire-v4 恢复进入 SELECT/ACK/READY 时，系统应让仍存活的旧句柄继续收发；只有新会话通过最终协商并发布 `SessionResumed` 后，旧句柄才失效。
- 当 wire-v4 恢复协商超时、控制发送失败或新会话关闭时，系统应清理新会话和临时映射，但保留仍存活的旧会话。
- 当 completed 业务事件已占满本次公开容量时，系统仍应有界、非阻塞地消化底层事件，使认证心跳 ACK 和协议控制不会被业务积压饿死；新公开事件按原顺序留在 completed 队列。
- 当 `poll(0, ...)` 或 C `rnet_game_poll_events(..., capacity=0, ...)` 被调用时，系统应不阻塞、不返回事件，但仍推进待发冲刷、心跳、时钟和 v4 重试/超时；在不越过待上抛公开事件的前提下消化底层控制。

### 边界和异常

- 当允许明文业务且一个未验证完整性的业务 frame 无法解码为合法 envelope 时，系统应累计丢弃计数后静默丢弃，不关闭会话、不记录逐包日志、不产生 `ProtocolViolation` 应用事件。
- 当相同错误来自 Noise 验证过的业务 frame 或认证控制通道时，系统仍应关闭会话并上抛 `ProtocolViolation`。
- 非阻塞控制消化每次 poll 最多处理固定数量的底层事件，避免认证对端用持续控制流困住调用线程。
- 零容量或已满的公开输出不得把底层有界事件队列批量搬到可增长的延后队列；遇到首个需延后的公开事件即停止非阻塞消化。
- C 时钟快照中的 `available` 是 has-sample 判别位；服务端会话和尚未采样的客户端返回 `available=0`。偏移只表示两套进程内单调时钟之间的近似传输样本，不是 UTC 或反外挂可信时钟。

## 技术设计

### 模块划分

- **`runtime.rs`**：区分 v3 立即接管和 v4 Ready 后接管。
- **`poll_runtime.rs`**：统一有界非阻塞底层事件消化、零容量维护和明文错误分类。
- **`range_runtime.rs`**：在 `publish_range_ready` 完成 v4 旧句柄撤销，失败路径只清理新会话。
- **`observe.rs`**：提供明文非法 envelope 累计快照及 Prometheus 计数。
- **C ABI/文档**：零容量 poll 调用 Rust 维护路径；明确时钟 `available` 语义，不改变 ABI 布局。

### 纯度边界

- **纯逻辑**：错误是否属于未验证明文、v3/v4 接管时点、计数快照。
- **副作用**：底层事件轮询、会话关闭、控制发送和计时器推进。

## 兼容性

不改变 wire v3/v4、C 结构布局或公开收发参数。零容量 poll 从“完全不推进”收紧为“非阻塞维护”，明文非法业务输入从公开违规事件变为可观测的静默丢弃；认证输入仍保持 fail-closed。
