# 游戏业务记录完整性来源

## 需求概述

同一游戏运行时可由服务端切换业务加密模式。处理格式错误的业务消息时，不能仅凭运行时“允许明文”配置判断是否断线；必须依据该条入站记录实际是否经过认证。

## 行为规格

- 当业务记录由 Noise 保护并通过认证时，游戏 envelope 或路由元数据错误应报告 `ProtocolViolation` 并关闭会话。
- 当业务记录为显式允许的明文时，游戏 envelope 或路由元数据错误应报告 `ProtocolViolation`，但不得仅因此关闭会话。
- 当受保护的内部控制错误时，仍须关闭会话。
- 当服务端在已建立会话中切换加密模式时，前后入站事件分别按实际记录来源处理，不以当前模式推断历史记录。

## 技术设计

- `rnet-core::Event` 附加仅供库内使用的完整性来源位，默认未认证。它不是网络字段，不改变 C ABI 或游戏业务事件格式。
- 传输层在成功解密的业务记录上设置来源位；适配 TCP/UDP/KCP 的 `PlainData` 保持未认证。旧兼容传输消息也保持未认证。
- `rnet-game` 仅在运行时允许明文、事件是业务消息且该记录未认证时放宽强制关闭；其他错误仍 fail-closed。
- 明文模式的底层记录格式损坏仍可能导致传输层断线。本任务不承诺明文具备抗篡改能力，也不改变 wire 协议。

## 任务拆解

- [x] 先补回归测试：明文伪造 envelope 不踢人；同一会话切回加密后，认证业务 envelope 错误仍踢人。
- [x] 传输层向事件传递记录完整性来源，并覆盖 TCP/UDP/KCP 的统一接收路径。
- [x] 游戏层按单条事件来源执行关闭策略；更新安全文档的边界。
- [x] 全量回归、ABI 检查、对抗性审查。明文外层记录可被篡改导致传输断线的既有边界已在使用文档明确列出。
